# ADR-PROC-0001: Рабочий цикл — проблема → тест → фикс

**Статус:** Proposed
**Создано:** 2026-10-02
**Обновлено:** 2026-10-02

## Контекст

Любое изменение кода начинается с проблемы. Без фиксации проблемы до изменения
невозможно понять, что изменение вообще что-то решает. Без теста невозможно
понять, что проблема не вернётся.

Цена написания тестов с LLM низкая. Цена ошибки — высокая. Значит, тесты
пишутся всегда, когда есть проблема.

Этот ADR — фундамент процесса для проекта News Feed Factory. На него ссылаются
ADR-PROC-0002 и ADR-ARCH-*.

## Решение

### Основной цикл

1. **Проблема.** Формулируется явно: что не работает, что должно работать,
   чего не хватает. Обязательно содержит описание ожидаемого поведения, а не
   только текущего состояния.

2. **Тест.** Пишется тест, подтверждающий проблему. Перед написанием задаём
   вопрос: «Это желаемое поведение или просто то, как оно сейчас работает?».
   Если тест фиксирует текущее (пусть и кривое) поведение — это
   characterization test; он пишется отдельно для понимания контекста и
   удаляется, когда написан настоящий тест на проблему.

   Тест должен покрывать граничные случаи, явно указанные в описании проблемы.
   Не «все возможные», а те, которые относятся к проблеме.

3. **Проверка падения.** Если тест не падает — проверяем ещё раз, что он
   действительно проверяет то, что нужно. Фиксируем, что проблема не
   воспроизводится:
   - Комментарий к тесту: `// Проблема X не воспроизвелась на момент Y. Тест оставлен как защита.`
   - В issue: короткая заметка «не воспроизвелось, тест оставлен» + ссылка на коммит.

   Оставляем тест. Идём дальше.

4. **Решение.** Изменение, достаточное для прохождения теста, и не более.

5. **Проверка.** Тест проходит.

6. **Рефакторинг.** Опционально, если нужен.

### Один цикл для всего

Тот же цикл применяется для:

- Новой функциональности — тест до реализации.
- Багов — тест, воспроизводящий баг, до фикса.
- Legacy — тест, фиксирующий проблему, до изменения.
- Рефакторинга — тесты зелёные до и после.

Отдельных правил для legacy или багов нет. Цикл один.

### Тест остаётся

Тест, написанный на шаге 2, остаётся в кодовой базе после фикса. Он не
удаляется.

Это и есть механизм измерения: если проблема вернётся — тест упадёт. Не метрика,
не отчёт, а сам тест.

Исключение: тест удаляется, если проблема, которую он фиксирует, больше не
актуальна. Решение об удалении — явное, не случайное.

### Тесты и скорость

Скорость локального прогона критична для соблюдения цикла. Медленные тесты —
это блокер дисциплины, а не «известная проблема».

Правила:

- Локальный прогон должен выполняться быстро.
- Если тест медленный из-за внутренних зависимостей (БД, файловая система,
  тяжёлые вычисления) — применяем моки, фикстуры или специализированные
  средства ускорения.
- Если тест требует внешних API, сети, сторонних сервисов или тяжёлых
  зависимостей — он помечается как `@group integration` и исключается из
  локального прогона по умолчанию. Такие тесты запускаются отдельно (в CI
  или по явному флагу).
- Оптимизация тестов — не «когда станет больно», а сразу, как только тест
  начинает тормозить локальный цикл.

### Тесты и LLM

Тесты пишет LLM. Ревью — ситуативное:

- При падении теста без очевидной причины — проверяю: тест проверяет
  поведение или реализацию? Нет ли лишних интеграционных точек?
- Периодически пересматриваю набор тестов, если быстро растёт объём или
  время прогона. Критерии: тесты дублируют друг друга, тестируют реализацию
  вместо поведения, или замедляют локальный прогон.

### Инструменты

- **Framework:** PHPUnit (по умолчанию). Pest — допустим, но PHPUnit
  предпочтителен: меньше магии, легче для LLM.
- **Unit-тесты:** `tests/unit/`, без БД, быстрые.
- **Integration-тесты:** `tests/integration/`, с реальной БД WordPress
  (wp-env или test suite). Помечаются `@group integration`.

## Последствия

**Плюсы:**

- Проблема зафиксирована до изменения — понятно, что решаем.
- Ожидаемое поведение описано явно — меньше споров о том, что считать «правильным».
- Возврат проблемы обнаруживается автоматически.
- Единый цикл для всех типов задач — не надо помнить разные правила.
- Тесты накапливаются и защищают код.
- Интеграционные тесты не тормозят локальную разработку.

**Минусы:**

- Изменение занимает больше времени, чем «поправить и забыть».
- Требуется дисциплина: не пропускать шаги 1–3.
- Тесты от LLM без обязательного ревью могут накопить хрупкие или дублирующие
  тесты — нужен периодический пересмотр.

**Риски:**

- Тест может фиксировать неправильное поведение. Решение: перечитать
  формулировку проблемы и явно заданный ожидаемый результат перед написанием
  теста.
- Тест может быть слишком слабым и не ловить возврат. Решение: пересматривать
  тесты при повторных багах.
- LLM генерирует хрупкие тесты, привязанные к реализации. Решение: ревью по
  чек-листу выше.

## Альтернативы

- **Тесты после кода.** Отклонено: не подтверждают проблему, не гарантируют
  возврат.
- **Тесты только для критичного кода.** Отклонено: цена ошибки высока везде,
  а цена теста с LLM низкая.
- **Разные правила для фич и багов.** Отклонено: усложняет процесс, ведёт к
  путанице.
- **Без тестов, ручная проверка.** Отклонено: не масштабируется, не защищает
  от возврата.
- **Все тесты в локальном прогоне.** Отклонено: интеграционные тесты ломают
  скорость локального цикла; вынесены отдельной категорией.
