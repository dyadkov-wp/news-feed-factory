# ADR-ARCH-0002: Нормализация контента

**Статус:** Proposed
**Создано:** 2026-10-02
**Обновлено:** 2026-10-09

## Контекст

Ядро (ADR-ARCH-0001) собирает записи и метаданные, но отдаёт их «как есть»:
сырой HTML из `post_content`, дату строкой, featured image как ID. Каждый
рендерер, если нормализации нет, будет делать одно и то же по-своему:
чистить HTML, декодировать entities, резать длинные поля, искать картинку,
форматировать дату.

Это ведёт к дублированию, расхождениям в качестве очистки и невозможности
тестировать нормализацию отдельно от рендера. Нужен общий слой нормализации
между сборщиком и рендерерами.

## Решение

### Слой нормализации

Новый слой между `Collector` и `Renderer`:

```
Collector → ContentNormalizer → Renderer
```

Нормализация — **в ядре, не в рендерере** (вариант A обсуждения). Рендерер
получает уже подготовленный массив. Причина: одно место для однотипных
операций, тестируемость, тонкие рендереры.

### Структура файлов

Добавляется подпапка `src/Normalize/`:

```
src/
├── Normalize/
│   ├── ContentNormalizer.php    # фасад, вызывает остальных
│   ├── HtmlSanitizer.php        # sanitize + decode + редакционные вырезы
│   ├── Truncator.php            # ресурсный и форматный обрез
│   └── ImageExtractor.php       # featured / первая картинка
```

Разделение на подклассы — по одной ответственности. `ContentNormalizer` —
точка входа, остальное — детали.

### Расширение интерфейса рендерера

`RendererInterface` (ADR-ARCH-0001) дополняется методом:

```php
public function get_normalization_config(): array;
```

Метод возвращает **требования рендерера к нормализации**. Ядро мёржит их
с дефолтами и передаёт в `ContentNormalizer`.

Причина: нормализатор не должен знать о конкретных рендерах. Рендер сам
объявляет, что ему нужно: лимиты, режим обрезки, whitelist тегов,
минимальные размеры картинок.

Дефолтная конфигурация (используется, если рендер вернул пустой массив):

| Параметр | Дефолт | Смысл |
| --- | --- | --- |
| `max_content_length` | `null` | Ресурсный лимит на сырой HTML |
| `truncate_mode` | `'none'` | Режим обрезки формата: `none`, `chars`, `words`, `first_paragraph` |
| `truncate_limit` | `0` | Порог обрезки формата (символы или слова, зависит от режима) |
| `allowed_html` | базовый набор `wp_kses` | Whitelist тегов |
| `image_min_width` | `null` | Минимальная ширина картинки |
| `image_min_height` | `null` | Минимальная высота картинки |
| `include_terms` | `false` | Включать ли рубрики и теги в нормализованный элемент |

### Нормализованный элемент

На выходе `ContentNormalizer::normalize()` — ассоциативный массив:

```php
[
    'id'             => string,             // get_permalink()
    'link'           => string,             // URL
    'title'          => string,             // plain, decoded
    'content'        => string,             // sanitized HTML, обрезанный
    'excerpt'        => string,             // plain, decoded, обрезанный
    'published'      => \DateTimeImmutable, // в UTC
    'author'         => string,             // display_name, '' если нет
    'image_url'      => ?string,            // null, если нет
    'image_width'    => ?int,
    'image_height'   => ?int,
    'terms'          => array,              // пусто, если include_terms = false
]
```

`terms` — плоский список:

```php
[
    ['taxonomy' => 'category', 'id' => 12, 'name' => 'Политика', 'slug' => 'politika'],
    ['taxonomy' => 'post_tag', 'id' => 686, 'name' => 'Интервью', 'slug' => 'intervyu'],
]
```

### Порядок обработки

Два разных пайплайна для двух полей контента плюс отдельные процедуры
для заголовка, даты, картинки и терминов. Общая идея: сначала защита,
потом форматирование.

**`content` — sanitized HTML.** Остаётся HTML после обработки: этого
требует `yandex:full-text` (CDATA с разметкой). Форматная обрезка
(`truncate_mode`) к `content` **не применяется** — Яндекс хочет полный
текст.

1. Ресурсный лимит `max_content_length` — до sanitize, на сырой HTML.
2. `HtmlSanitizer::sanitize( $html, $allowed_html )` — whitelist тегов
   и атрибутов, HTML остаётся.
3. Редакционные вырезы `content_filters` — если заданы в конфиге.

**`excerpt` — plain text.** Теряет все теги: этого требуют `description`
в RSS и подобные поля. Абзацы сохраняются как `\n\n`.

1. Ресурсный лимит `max_content_length` — до всех преобразований.
2. `HtmlSanitizer::to_plain( $html )` — decode entities, блочные теги →
   `\n\n`, остальные теги удалены.
3. `Truncator::truncate( $plain, $mode, $limit )` — если
   `$config['truncate_mode'] !== 'none'`.

Редакционные вырезы `content_filters` к `excerpt` **не применяются**:
они работают с HTML (убрать блок «читайте также», соцкнопки), к
plain-тексту неприменимы.

**Заголовок.** Декодирование entities + trim. Форматная обрезка на
уровне нормализатора не делается — `Truncator` вызывается рендерером,
если формат канала требует (например, Яндекс требует 200 символов, см.
ADR-ARCH-0003).

**Дата.** `post_date_gmt` → `DateTimeImmutable` в UTC. Формат (RFC 2822
или W3C) применяет рендерер — нормализатор отдаёт объект.

**Картинка и термины.** Извлекаются в `Collector`, до
`ContentNormalizer` — там, где уже есть доступ к `$post_id` и WP-API.
Нормализатор получает готовые `image_*` и `terms` в `$raw`.

Ресурсный лимит `max_content_length` — **до** санитизации: цель — не
гонять regex по гигантской строке. Форматная обрезка `truncate_limit` —
**после** санитизации: цель — уложиться в эстетический лимит канала.

### Ресурсный лимит vs форматная обрезка

Те же два разных лимита, что в ADR-ARCH-0001 обсуждении, но теперь оба
относятся к нормализации:

| Лимит | Цель | Где задаётся | Когда применяется |
| --- | --- | --- | --- |
| `max_content_length` | Защита ресурсов | Рендер (или дефолт `null`) | До sanitize, только к `content` |
| `truncate_limit` | Формат канала | Рендер | После санитизации |

Не смешивать. Первый — про память и CPU. Второй — про эстетику.

### Контракт Truncator

`Truncator::truncate( string $text, string $mode, int $limit ): string`

**Вход** — plain text, абзацы разделены `\n\n`. HTML к моменту вызова
уже удалён `HtmlSanitizer::to_plain()`. Truncator HTML не разбирает и
не удаляет.

**Режимы:**

| `mode` | `limit` | Поведение |
| --- | --- | --- |
| `none` | игнорируется | текст без изменений |
| `chars` | символы | до N символов по последнему полному слову |
| `words` | слова | первые N слов |
| `first_paragraph` | символы | первый абзац; при `limit > 0` ужать по словам |

**Правила:**

- `limit <= 0` — «не обрезать по длине». Режим сохраняется:
  `first_paragraph` вернёт весь первый абзац, `chars`/`words` — весь
  текст.
- Граница обрезки — всегда **полное слово**. Часть слова не отдаём.
- Многоточие не добавляется — это ответственность вызывающего кода.
- Две оси независимы: `mode` выбирает фрагмент, `limit` — длину.
- Пустая строка или строка из пробелов → пустая строка.

**Примеры** (`\n\n` — граница абзаца):

```
truncate( "hello world", "chars", 7 )                   → "hello"
truncate( "hello world", "words", 1 )                   → "hello"
truncate( "a\n\nb\n\nc", "first_paragraph", 0 )         → "a"
truncate( "hello world\n\nnext", "first_paragraph", 3 ) → "hello"
truncate( "hello world", "none", 5 )                    → "hello world"
truncate( "hello world", "chars", 0 )                   → "hello world"
truncate( "verylongword short", "chars", 5 )            → ""
```

Расхождение с Python-референсом (`content_transform.py::truncate`):
там режим `words` фактически режет **по символам**, сохраняя абзацы;
здесь `chars` и `words` — две разные единицы измерения. Если понадобится
сохранение абзацев при обрезке по символам — отдельный режим, отдельным
ADR.

### Контракт HtmlSanitizer::to_plain

`HtmlSanitizer::to_plain( string $html ): string`

Преобразует rendered HTML в plain text с абзацами через `\n\n`.
Используется перед `Truncator` для `excerpt`. Для `content`
(`yandex:full-text`) не применяется — Яндекс получает sanitized HTML
как есть.

Порядок операций:

1. Декодирование HTML-entities (`html_entity_decode`, `ENT_QUOTES |
   ENT_HTML5`, UTF-8).
2. Non-breaking space (U+00A0) → обычный пробел.
3. Блочные теги (`<p>`, `<div>`) → `\n\n`. Открывающий и закрывающий
   обрабатываются одинаково — `</p>` тоже даёт `\n\n`.
4. `<br>`, `<br/>`, `<br />` → `\n`.
5. Удаление остальных тегов.
6. Удаление маркера обрыва в конце текста: `[…]` или `[...]`.
7. Нормализация: 3+ `\n` → `\n\n`; схлопывание пробелов и табов внутри
   абзаца до одного; trim каждого абзаца; пустые абзацы удаляются.

`wp_kses` здесь не вызывается — sanitize отдельный метод. `to_plain`
работает с уже sanitized HTML или с rendered HTML, полученным из REST.

**Пример** (типичный `excerpt.rendered` из WP):
```text
вход: <p>Торжественная церемония … состоялась в Екатеринбурге. … […]</p>
выход: Торжественная церемония … состоялась в Екатеринбурге
```

### Контракт HtmlSanitizer::sanitize

`HtmlSanitizer::sanitize( string $html, ?array $allowed_html = null ): string`

Очищает HTML по whitelist'у тегов и атрибутов. Вызывается в
нормализации контента после ресурсного лимита и до редакционных
вырезов (см. «Порядок обработки»).

**Поведение:**

- `$allowed_html === null` → `wp_kses_post( $html )`, встроенный
  пост-whitelist WordPress.
- `$allowed_html` — массив формата `wp_kses` (`['a' => ['href' =>
  true, 'title' => true], 'p' => []]`) → `wp_kses( $html,
  $allowed_html )`.
- `$allowed_html === []` → пустой whitelist, все теги вырезаются,
  остаётся только plain text. Это отличается от `null` (дефолт).
- Пустая строка на входе → пустая строка на выходе.
- HTML без тегов → возвращается как есть.

`wp_kses` не декодирует entities, не трогает пробелы, не удаляет
маркер обрыва. Всё это — задачи соседних методов (`to_plain`).

**Согласование с `get_normalization_config()`.** Рендер возвращает
`allowed_html`. Если ключ отсутствует или `null` — используется
дефолт (`wp_kses_post`). Если массив — передаётся как есть.

**Примеры:**

```
sanitize( '<p>Hello</p>', null )                        → '<p>Hello</p>'
sanitize( '<p>Hello</p>', [ 'p' => [] ] )               → '<p>Hello</p>'
sanitize( '<p><a href="#">Hi</a></p>', [ 'p' => [] ] )  → '<p>Hi</p>'
sanitize( '<script>alert(1)</script>', null )           → ''
```

**Тестирование:** integration (`@group integration`), так как `wp_kses`
загружается WordPress test suite. В unit-прогон не входит.

### Контракт ImageExtractor

`ImageExtractor::extract( int $post_id, array $config ): ?array`

Достаёт featured image записи и возвращает `url`, `width`, `height`.
Применяет пороги `image_min_width` / `image_min_height` из конфига
нормализации.

**Возврат:**

```php
[
    'url'    => string,   // абсолютный URL
    'width'  => int,      // ширина в пикселях
    'height' => int,      // высота в пикселях
]
```

или `null`, если изображения нет или оно отброшено.

**Порядок:**

1. `get_post_thumbnail_id( $post_id )`. Нет ID → `null`.
2. `wp_get_attachment_image_src( $attachment_id, 'full' )`. Возвращает
   `false` (битый ID) → `null`.
3. Пороги: `image_min_width` и `image_min_height`. Значение `null` или
   `0` — фильтр не применяется. Иначе `width < min` → `null`,
   `height < min` → `null`. Оба порога проверяются независимо, при
   провале любого — `null`.
4. Иначе — массив с `url`, `width`, `height`.

**Размер `'full'`** — оригинал вложения. Замена на `large`/`medium` не
вводится: ADR-PRODUCT-0001 не требует ужимать картинку в фиде, а
рендерер сам решает, что делать с URL. Если понадобится — отдельным
ADR.

**Поиск картинки в контенте** (если featured нет) остаётся открытым
вопросом ADR — этот метод его не закрывает.

**Тестирование:** integration (`@group integration`), так как нужны
`WP_UnitTestCase::factory()`, `set_post_thumbnail()` и реальное
вложение. В unit-прогон не входит.

### Контракт ContentNormalizer::normalize

`ContentNormalizer::normalize( array $raw, array $config ): ?array`

Фасад слоя нормализации. Принимает «сырой» массив от `Collector`,
возвращает нормализованный элемент (см. «Нормализованный элемент») или
`null`, если запись нельзя отдать в фид.

**Форма `$raw`.** Фиксированная структура, а не конфигурируемый список
полей. Отличие от REST-источника: у нас `Collector` работает с
`WP_Query`, набор полей известен заранее. Форма:

```php
[
    'id'           => string,       // get_permalink()
    'link'         => string,
    'title'        => string,       // rendered HTML (entities допустимы)
    'content'      => string,       // УЖЕ sanitized HTML (Collector применил wp_kses)
    'excerpt'      => string,       // rendered HTML (raw)
    'published'    => string,       // MySQL datetime (post_date_gmt)
    'author'       => string,       // display_name, '' если нет
    'image_url'    => ?string,      // результат ImageExtractor
    'image_width'  => ?int,
    'image_height' => ?int,
    'terms'        => array,        // плоский список (см. «Нормализованный элемент»)
]
```

**Почему `content` приходит уже sanitized, а `excerpt` — нет.** Это
следствие разделения WP-зависимостей. `HtmlSanitizer::sanitize()`
требует `wp_kses` (WP-функция), поэтому вызывается в `Collector` — на
границе с WP. `HtmlSanitizer::to_plain()` — чистый PHP, поэтому
вызывается внутри `ContentNormalizer`. Такое разделение делает
`ContentNormalizer` unit-тестируемым: внутри нет WP-функций.

**Форма `$config`.** Из `RendererInterface::get_normalization_config()`,
смёрженная с дефолтами. Полный набор ключей — в таблице выше.

**Порядок обработки полей:**

1. **Обязательные поля.** Если `id`, `link` или `title` — пустая строка
   или не строка → `null` (пропуск записи).
2. **Дата.** `published`: пусто, `'0000-00-00 00:00:00'`, `null` или не
   парсится `DateTimeImmutable` → `null`. Иначе —
   `setTimezone( new DateTimeZone( 'UTC' ) )`.
3. **Автор.** Переносится как есть из `$raw`. Пустая строка,
   если поля нет. Форматирование (эскейпинг в XML) — в рендерере.
4. **Заголовок.** `html_entity_decode` + trim.
5. **`content`.** Переносится как есть (уже sanitized в `Collector`).
6. **`excerpt`.** `HtmlSanitizer::to_plain()`, затем
   `Truncator::truncate()`, если `truncate_mode !== 'none'`.
7. **`image_*`.** Переносятся как есть из `$raw`. Пороги
   `image_min_width` / `image_min_height` уже применил `ImageExtractor`
   в `Collector` — повторная проверка не делается.
8. **`terms`.** Если `include_terms = false` — `[]`. Иначе — как пришло
   из `Collector` (порядок: сначала категории по `name`, потом теги по
   `name`).

**Возврат.** Ассоциативный массив из секции «Нормализованный элемент»
или `null`. Ключ `terms` присутствует всегда (пустой массив при
`include_terms = false`).

**Разделение ответственности:**

- `Collector` — всё, что требует WP API: `WP_Query`, метаданные,
  `ImageExtractor`, `wp_get_post_terms()`, `HtmlSanitizer::sanitize()`
  для `content`, `content_filters`.
- `ContentNormalizer` — чистые преобразования: валидация обязательных
  полей, парсинг даты, decode заголовка, `to_plain` для `excerpt`,
  `Truncator`, сборка выходного массива.

### Обрезка mid-tag

Если ресурсный лимит попал в середину HTML-тега (`<a href="https://examp`),
закрывающий `>` не появится, и `wp_kses` этот мусор не удалит. После
ресурсной обрезки — удаляем незавершённый тег:

```php
$cut = mb_substr( $text, 0, $limit );
$cut = preg_replace( '/<[^>]*$/u', '', $cut );
```

Одна строка, симметрично «мягкой обрезке»: результат может быть короче
лимита, зато без артефактов.

Форматная обрезка (после санитизации) работает по чистому тексту — там
проблемы нет.

### Редакционные вырезы

Общий интерфейс — массив идентификаторов в конфиге рендера:

```php
'content_filters' => [ 'strip_social_links', 'strip_related_block' ],
```

Каждый идентификатор регистрируется через фильтр `nwff_content_filters`
как callable: `function( string $html ): string`. Встроенные вырезы — набор
в ядре (пустой на этапе 1, рендереры добавляют свои).

Причина: конкретные вырезы — специфика формата (Яндекс запрещает одни
блоки, Дзен — другие). Общий — только механизм вызова.

### Обработка ошибок

Нормализация **не роняет фид**. Правила по уровням:

**Пропуск записи (`normalize` возвращает `null`):**

- `id` отсутствует, пустой или не строка.
- `link` отсутствует, пустой или не строка.
- `title` отсутствует, пустой или не строка.
- `published` пуст, равен `'0000-00-00 00:00:00'`, `null`, или
  `new DateTimeImmutable( $value )` бросает исключение.

Пропуск сопровождается `WARNING` в лог с указанием, какое поле
отсутствовало.

**Не пропуск, но заполнение дефолтом:**

- `content` пуст → `content = ''`. `WARNING` в лог.
- `excerpt` пуст или `to_plain` вернул пустую строку →
  `excerpt = ''`. Без `WARNING`: WP отдаёт пустой excerpt штатно.
- `image_url` отсутствует (`null`) → `image_url = null`,
  `image_width = null`, `image_height = null`. Без `WARNING`: у поста
  может не быть featured image — это норма.
- `terms` отсутствует или не массив → `terms = []`. Без `WARNING`.

**Внутренние ошибки:**

- `ImageExtractor` вернул `null` из-за битого attachment ID — `WARNING`
  уже записан в `Collector`, `ContentNormalizer` просто получает
  `image_url = null`.
- Исключение в `content_filter` — `WARNING`, фильтр пропускается,
  остальные вырезы применяются. Это происходит в `Collector`, до
  `ContentNormalizer`.

**Логика.** Пост без картинки — публикуем. Пост без excerpt —
публикуем (в шаблоне рендера `description` может быть опциональным,
ADR-ARCH-0003). Пост без id/link/title/даты — не публикуем. Правило
согласуется с общим подходом: не падать на аномалиях источника, но и
не отдавать в фид заведомо неполные данные.

### Точки расширения

- `nwff_allowed_html` — фильтр whitelist тегов.
- `nwff_content_filters` — регистрация редакционных вырезов.
- `nwff_image_min_dimensions` — переопределение минимальных размеров.
- `nwff_normalized_item` — финальный фильтр нормализованного элемента.
- `nwff_normalization_config` — внешняя правка конфигурации нормализации
  (после мёржа дефолтов с требованиями рендера).

Первые три — для внешних плагинов. Четвёртый — для совсем крайних случаев.
Пятый — на случай, если фильтр нужно наложить «поверх всего».

### Тестирование

- **Unit:** `Truncator`, `HtmlSanitizer::to_plain`, `ContentNormalizer`
  (с фикстурами `$raw`). Все три работают без WordPress.
- **Integration:** `HtmlSanitizer::sanitize` (требует `wp_kses`),
  `ImageExtractor` (требует attachment), `terms` (требует таксономий).
  Помечаются `@group integration`.

`ContentNormalizer` — unit, потому что все WP-зависимости вынесены в
`Collector` (см. «Контракт ContentNormalizer::normalize»). Внутри
класса — только чистые PHP-вызовы: `html_entity_decode`,
`DateTimeImmutable`, `HtmlSanitizer::to_plain`, `Truncator::truncate`.

## Последствия

**Плюсы:**

- Одна точка для однотипных операций — не дублируется по рендерам.
- Рендерер тонкий: получает готовые данные, отвечает только за XML.
- Нормализация тестируется отдельно от форматов.
- Требования рендера к нормализации — явный контракт через интерфейс.
- Два разных лимита (ресурсный / форматный) чётко разделены.
- Обработка ошибок единообразна.

**Минусы:**

- Ещё один слой между сборщиком и рендером — больше кода.
- Дополнительный проход по контенту на каждый запрос ленты (компенсируется
  кэшем).
- Интерфейс рендерера расширяется — надо обновить ADR-ARCH-0001 и
  заготовки.

**Риски:**

- `wp_kses` может вырезать нужное, если whitelist слишком узкий. Решение:
  дефолтный whitelist — консервативный, рендер расширяет.
- `mb_substr` на очень больших строках (несколько МБ) — линейно по длине,
  но не критично при кэше.
- Порядок вырезов может влиять на результат. Решение: вырезы применяются
  в порядке объявления в конфиге рендера.

## Альтернативы

- **Нормализация в рендере (вариант B).** Отклонено: дублирование,
  расхождения, тонкий рендер невозможен.
- **Нормализация в Collector.** Отклонено: Collector — про выборку и
  метаданные, не про форматирование контента.
- **Один класс `ContentNormalizer` без подклассов.** Отклонено: с ростом
  логики класс превратится в свалку. Разделение сейчас — дешевле, чем
  рефакторинг потом.
- **Интерфейс рендерера без `get_normalization_config()`.** Отклонено:
  тогда требования к нормализации пришлось бы прокидывать через фильтр —
  менее явно. Метод в интерфейсе — обязательный контракт.
- **Обрезка только одна — форматная.** Отклонено: без ресурсного лимита
  гигантские `post_content` пройдут через `wp_kses` целиком.
- **Обрезка только одна — ресурсная.** Отклонено: тогда рендер не сможет
  уложиться в эстетический лимит канала.
- **Редакционные вырезы — в рендере.** Отклонено: интерфейс общий, смысл
  общий; конкретика — в рендере. Дублировать механизм вызова в каждом
  рендере — избыточно.
- **Поиск картинок в контенте сразу.** Отклонено на этапе 1: featured
  image покрывает большинство случаев. См. открытые вопросы.
- **Падение на битой дате вместо пропуска.** Отклонено: пропуск с
  `WARNING` устойчивее, фид не разваливается из-за одного поста.

## Ссылки

- **Зависит от:** ADR-PRODUCT-0001 (продукт), ADR-ARCH-0001 (ядро),
  ADR-PROC-0001 (рабочий цикл), ADR-PROC-0002 (документация и ADR).
- **Уточняется в:** ADR-ARCH-0003 (рендерер Яндекса — задаёт свой
  `get_normalization_config()`), ADR-ARCH-0004 (Google, Proposed),
  ADR-ARCH-0005 (Дзен, Proposed).
- **Связано с:** нет.

## Открытые вопросы

- **Поиск картинки в контенте.** Если featured image нет, но есть
  `<img>` в `post_content` — использовать ли? Пока — нет. Если понадобится
  (скорее всего, для Дзена) — отдельный ADR с правилами извлечения и
  определением размеров.
- **Размеры картинок при внешнем URL.** `wp_get_attachment_image_src`
  возвращает размеры для локальных вложений. Для картинок с внешних
  хостингов — размеры неизвестны без скачивания. Пока не решаем.
- **Формат даты — в рендере или в нормализаторе?** Сейчас — в рендере
  (нормализатор отдаёт `DateTimeImmutable`). Если окажется, что все
  рендеры используют RFC 2822, кроме sitemap — можно закрепить дефолт.
  Пока — решает рендер.
- **Кэширование нормализованных элементов.** Сейчас кэш — на готовом XML
  (ADR-ARCH-0001). Нормализация кэшируется неявно, как часть генерации.
  Если появится второй рендер с теми же данными, но другим форматом —
  возможно, имеет смысл кэшировать нормализованный массив отдельно.
  Пока — нет.
- **Plain-версия полного `content`.** Сейчас `content` остаётся
  sanitized HTML — этого требует `yandex:full-text`. Но может появиться
  рендер, которому нужен plain text **полного** контента (например,
  RSS для ВК с `first_paragraph`, взятым от `content`, а не от
  `excerpt`). Тогда — либо отдельный конфиг-ключ
  (`content_mode = 'html' | 'plain'`), либо второе поле
  `content_plain` в нормализованном элементе. Пока не решаем (YAGNI):
  `Truncator` уже умеет `first_paragraph`, вопрос только в том, откуда
  брать plain. Возвращаемся, когда появится конкретный рендер.
