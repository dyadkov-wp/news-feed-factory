# ADR-ARCH-0002: Нормализация контента

**Статус:** Proposed
**Создано:** 2026-10-02
**Обновлено:** 2026-10-09

## Контекст

Ядро (ADR-ARCH-0001) собирает записи и метаданные, но отдаёт их «как есть»:
сырой HTML из `post_content`, дату строкой, featured image как ID. Каждый
рендерер, если нормализации нет, будет делать одно и то же по-своему:
чистить HTML, декодировать entities, резать длинные поля, искать картинку,
форматировать дату.

Это ведёт к дублированию, расхождениям в качестве очистки и невозможности
тестировать нормализацию отдельно от рендера. Нужен общий слой нормализации
между сборщиком и рендерерами.

## Решение

### Слой нормализации

Новый слой между `Collector` и `Renderer`:

```
Collector → ContentNormalizer → Renderer
```

Нормализация — **в ядре, не в рендерере** (вариант A обсуждения). Рендерер
получает уже подготовленный массив. Причина: одно место для однотипных
операций, тестируемость, тонкие рендереры.

### Структура файлов

Добавляется подпапка `src/Normalize/`:

```
src/
├── Normalize/
│   ├── ContentNormalizer.php    # фасад, вызывает остальных
│   ├── HtmlSanitizer.php        # sanitize + decode + редакционные вырезы
│   ├── Truncator.php            # ресурсный и форматный обрез
│   └── ImageExtractor.php       # featured / первая картинка
```

Разделение на подклассы — по одной ответственности. `ContentNormalizer` —
точка входа, остальное — детали.

### Расширение интерфейса рендерера

`RendererInterface` (ADR-ARCH-0001) дополняется методом:

```php
public function get_normalization_config(): array;
```

Метод возвращает **требования рендерера к нормализации**. Ядро мёржит их
с дефолтами и передаёт в `ContentNormalizer`.

Причина: нормализатор не должен знать о конкретных рендерах. Рендер сам
объявляет, что ему нужно: лимиты, режим обрезки, whitelist тегов,
минимальные размеры картинок.

Дефолтная конфигурация (используется, если рендер вернул пустой массив):

| Параметр | Дефолт | Смысл |
| --- | --- | --- |
| `max_content_length` | `null` | Ресурсный лимит на сырой HTML |
| `truncate_mode` | `'none'` | Режим обрезки формата: `none`, `chars`, `words`, `first_paragraph` |
| `truncate_limit` | `0` | Порог обрезки формата (символы или слова, зависит от режима) |
| `allowed_html` | базовый набор `wp_kses` | Whitelist тегов |
| `image_min_width` | `null` | Минимальная ширина картинки |
| `image_min_height` | `null` | Минимальная высота картинки |
| `include_terms` | `false` | Включать ли рубрики и теги в нормализованный элемент |

### Нормализованный элемент

На выходе `ContentNormalizer::normalize()` — ассоциативный массив:

```php
[
    'id'             => string,             // guid
    'link'           => string,             // URL
    'title'          => string,             // plain, decoded
    'content'        => string,             // sanitized HTML, обрезанный
    'excerpt'        => string,             // plain, decoded, обрезанный
    'published'      => \DateTimeImmutable, // в UTC
    'image_url'      => ?string,            // null, если нет
    'image_width'    => ?int,
    'image_height'   => ?int,
    'terms'          => array,              // пусто, если include_terms = false
]
```

`terms` — плоский список:

```php
[
    ['taxonomy' => 'category', 'id' => 12, 'name' => 'Политика', 'slug' => 'politika'],
    ['taxonomy' => 'post_tag', 'id' => 686, 'name' => 'Интервью', 'slug' => 'intervyu'],
]
```

### Порядок обработки

Для каждого поля — свой порядок, но общая идея: сначала защита, потом
форматирование.

**Контент и анонс:**

```
1. Ресурсный лимит (max_content_length) — до всего, на сырой HTML
2. Декодирование entities
3. Санитизация по allowed_html
4. Редакционные вырезы (content_filters)
5. Форматная обрезка (truncate_mode + truncate_limit)
```

Ресурсный лимит — **до** санитизации: цель — не гонять regex по гигантской
строке. Форматная обрезка — **после** санитизации: цель — уложиться в
эстетический лимит канала.

**Заголовок:** декодирование + plain.

**Дата:** `post_date_gmt` → `DateTimeImmutable` (UTC). Формат (RFC 2822
или W3C) применяет рендерер — нормализатор отдаёт объект.

**Картинка:**

```
1. Featured image (get_post_thumbnail_id + wp_get_attachment_image_src)
2. Если размеры меньше image_min_width / image_min_height — отбрасываем
3. Если нет featured — null (поиск в контенте — открытый вопрос)
```

**Термины:** если `include_terms = true` — `wp_get_post_terms()` для
категорий и тегов. Порядок — по имени.

### Ресурсный лимит vs форматная обрезка

Те же два разных лимита, что в ADR-ARCH-0001 обсуждении, но теперь оба
относятся к нормализации:

| Лимит | Цель | Где задаётся | Когда применяется |
| --- | --- | --- | --- |
| `max_content_length` | Защита ресурсов | Рендер (или дефолт `null`) | До санитизации |
| `truncate_limit` | Формат канала | Рендер | После санитизации |

Не смешивать. Первый — про память и CPU. Второй — про эстетику.

### Контракт Truncator

`Truncator::truncate( string $text, string $mode, int $limit ): string`

**Вход** — plain text, абзацы разделены `\n\n`. HTML к моменту вызова
уже удалён `HtmlSanitizer::to_plain()`. Truncator HTML не разбирает и
не удаляет.

**Режимы:**

| `mode` | `limit` | Поведение |
| --- | --- | --- |
| `none` | игнорируется | текст без изменений |
| `chars` | символы | до N символов по последнему полному слову |
| `words` | слова | первые N слов |
| `first_paragraph` | символы | первый абзац; при `limit > 0` ужать по словам |

**Правила:**

- `limit <= 0` — «не обрезать по длине». Режим сохраняется:
  `first_paragraph` вернёт весь первый абзац, `chars`/`words` — весь
  текст.
- Граница обрезки — всегда **полное слово**. Часть слова не отдаём.
- Многоточие не добавляется — это ответственность вызывающего кода.
- Две оси независимы: `mode` выбирает фрагмент, `limit` — длину.
- Пустая строка или строка из пробелов → пустая строка.

**Примеры** (`\n\n` — граница абзаца):

```
truncate( "hello world", "chars", 7 )                   → "hello"
truncate( "hello world", "words", 1 )                   → "hello"
truncate( "a\n\nb\n\nc", "first_paragraph", 0 )         → "a"
truncate( "hello world\n\nnext", "first_paragraph", 3 ) → "hello"
truncate( "hello world", "none", 5 )                    → "hello world"
truncate( "hello world", "chars", 0 )                   → "hello world"
truncate( "verylongword short", "chars", 5 )            → ""
```

Расхождение с Python-референсом (`content_transform.py::truncate`):
там режим `words` фактически режет **по символам**, сохраняя абзацы;
здесь `chars` и `words` — две разные единицы измерения. Если понадобится
сохранение абзацев при обрезке по символам — отдельный режим, отдельным
ADR.

### Обрезка mid-tag

Если ресурсный лимит попал в середину HTML-тега (`<a href="https://examp`),
закрывающий `>` не появится, и `wp_kses` этот мусор не удалит. После
ресурсной обрезки — удаляем незавершённый тег:

```php
$cut = mb_substr( $text, 0, $limit );
$cut = preg_replace( '/<[^>]*$/u', '', $cut );
```

Одна строка, симметрично «мягкой обрезке»: результат может быть короче
лимита, зато без артефактов.

Форматная обрезка (после санитизации) работает по чистому тексту — там
проблемы нет.

### Редакционные вырезы

Общий интерфейс — массив идентификаторов в конфиге рендера:

```php
'content_filters' => [ 'strip_social_links', 'strip_related_block' ],
```

Каждый идентификатор регистрируется через фильтр `nwff_content_filters`
как callable: `function( string $html ): string`. Встроенные вырезы — набор
в ядре (пустой на этапе 1, рендереры добавляют свои).

Причина: конкретные вырезы — специфика формата (Яндекс запрещает одни
блоки, Дзен — другие). Общий — только механизм вызова.

### Обработка ошибок

Нормализация **не роняет фид**. Правила:

- Картинка не найдена или отброшена по размеру → `image_url = null`,
  `WARNING` в лог.
- Featured image — битый attachment ID → `image_url = null`, `WARNING`.
- Дата невалидна → запись пропускается с `WARNING` (не публикуем без даты).
- Отсутствует `post_content` → `content = ''`, `WARNING`.
- Ошибка в `content_filter` (исключение) → `WARNING`, фильтр пропускается,
  остальные вырезы применяются.

Логика: пост без картинки — можно публиковать, пост без даты — нельзя.
Правило согласуется с общим подходом (не падать на аномалиях источника).

### Точки расширения

- `nwff_allowed_html` — фильтр whitelist тегов.
- `nwff_content_filters` — регистрация редакционных вырезов.
- `nwff_image_min_dimensions` — переопределение минимальных размеров.
- `nwff_normalized_item` — финальный фильтр нормализованного элемента.
- `nwff_normalization_config` — внешняя правка конфигурации нормализации
  (после мёржа дефолтов с требованиями рендера).

Первые три — для внешних плагинов. Четвёртый — для совсем крайних случаев.
Пятый — на случай, если фильтр нужно наложить «поверх всего».

### Тестирование

- **Unit:** `Truncator`, `HtmlSanitizer` (без WP-зависимостей или с
  моками). `ContentNormalizer` — с фикстурами.
- **Integration:** `ImageExtractor` (требует attachment), `terms`
  (требует таксономий). Помечаются `@group integration`.

## Последствия

**Плюсы:**

- Одна точка для однотипных операций — не дублируется по рендерам.
- Рендерер тонкий: получает готовые данные, отвечает только за XML.
- Нормализация тестируется отдельно от форматов.
- Требования рендера к нормализации — явный контракт через интерфейс.
- Два разных лимита (ресурсный / форматный) чётко разделены.
- Обработка ошибок единообразна.

**Минусы:**

- Ещё один слой между сборщиком и рендером — больше кода.
- Дополнительный проход по контенту на каждый запрос ленты (компенсируется
  кэшем).
- Интерфейс рендерера расширяется — надо обновить ADR-ARCH-0001 и
  заготовки.

**Риски:**

- `wp_kses` может вырезать нужное, если whitelist слишком узкий. Решение:
  дефолтный whitelist — консервативный, рендер расширяет.
- `mb_substr` на очень больших строках (несколько МБ) — линейно по длине,
  но не критично при кэше.
- Порядок вырезов может влиять на результат. Решение: вырезы применяются
  в порядке объявления в конфиге рендера.

## Альтернативы

- **Нормализация в рендере (вариант B).** Отклонено: дублирование,
  расхождения, тонкий рендер невозможен.
- **Нормализация в Collector.** Отклонено: Collector — про выборку и
  метаданные, не про форматирование контента.
- **Один класс `ContentNormalizer` без подклассов.** Отклонено: с ростом
  логики класс превратится в свалку. Разделение сейчас — дешевле, чем
  рефакторинг потом.
- **Интерфейс рендерера без `get_normalization_config()`.** Отклонено:
  тогда требования к нормализации пришлось бы прокидывать через фильтр —
  менее явно. Метод в интерфейсе — обязательный контракт.
- **Обрезка только одна — форматная.** Отклонено: без ресурсного лимита
  гигантские `post_content` пройдут через `wp_kses` целиком.
- **Обрезка только одна — ресурсная.** Отклонено: тогда рендер не сможет
  уложиться в эстетический лимит канала.
- **Редакционные вырезы — в рендере.** Отклонено: интерфейс общий, смысл
  общий; конкретика — в рендере. Дублировать механизм вызова в каждом
  рендере — избыточно.
- **Поиск картинок в контенте сразу.** Отклонено на этапе 1: featured
  image покрывает большинство случаев. См. открытые вопросы.
- **Падение на битой дате вместо пропуска.** Отклонено: пропуск с
  `WARNING` устойчивее, фид не разваливается из-за одного поста.

## Открытые вопросы

- **Поиск картинки в контенте.** Если featured image нет, но есть
  `<img>` в `post_content` — использовать ли? Пока — нет. Если понадобится
  (скорее всего, для Дзена) — отдельный ADR с правилами извлечения и
  определением размеров.
- **Размеры картинок при внешнем URL.** `wp_get_attachment_image_src`
  возвращает размеры для локальных вложений. Для картинок с внешних
  хостингов — размеры неизвестны без скачивания. Пока не решаем.
- **Формат даты — в рендере или в нормализаторе?** Сейчас — в рендере
  (нормализатор отдаёт `DateTimeImmutable`). Если окажется, что все
  рендеры используют RFC 2822, кроме sitemap — можно закрепить дефолт.
  Пока — решает рендер.
- **Кэширование нормализованных элементов.** Сейчас кэш — на готовом XML
  (ADR-ARCH-0001). Нормализация кэшируется неявно, как часть генерации.
  Если появится второй рендер с теми же данными, но другим форматом —
  возможно, имеет смысл кэшировать нормализованный массив отдельно.
  Пока — нет.
