# ADR-PROC-0002: Документация проекта и ADR

**Статус:** Proposed
**Создано:** 2026-10-02
**Обновлено:** 2026-10-08

## Контекст

Проектам нужна документация: чтобы понять, что это, как запустить, как
работать. Отдельно нужна память о решениях: почему сделано так, а не иначе.
Документация ради отчётности не нужна. Нужна документация для работы: человека
и LLM.

ADR — это формат записи решений. Он же — способ сохранить память о решениях
для LLM, которые не помнят прошлые чаты.

## Решение

### Документация проекта

Минимальный набор:

- **README.md** — что это, зачем, быстрый старт, технологии. На английском
  (по ADR-PRODUCT-0001, продукт класса А — open-source плагин).
- **readme.txt** — WordPress.org readme (стандартный формат репозитория).
  На английском.
- **doc/adr/index.md** — индекс ADR. На русском.
- **doc/adr/ADR-*.md** — сами ADR. На русском.

Остальное (CHANGELOG, CONTRIBUTING, FAQ) добавляется по мере боли, не заранее.
CHANGELOG ведётся, если продукт публикуется в репозитории.

### Формат ADR

- **Язык ADR — всегда русский.** ADR — память для владельца, а не для
  пользователей.
- **Код и имена файлов — английские.**
- **Комментарии в коде — английские.**
- **Имя файла:** `ADR-<ТИП>-<NNNN>-<короткое-имя>.md`.
- **Короткое имя** — английское, через дефис.
- **Нумерация** — четыре цифры с ведущими нулями, отдельная для каждого типа.
- **Статусы:** `Proposed`, `Accepted`, `Deprecated`, `Superseded`.

### Типы ADR

| Тип | Отвечает на вопрос | Пример |
| --- | --- | --- |
| `PRODUCT` | Что делаем и зачем | Что делаем, форматы, этапы |
| `ARCH` | Как устроено внутри | «Кастомная таблица `nwff_feed_meta`» |
| `PROC` | Как мы работаем | «TDD обязателен» |

`DESIGN` — не используем на старте. Если понадобится детальное описание
функции, заведём отдельным решением.

### Где живут ADR

Один уровень: в репозитории продукта, папка `doc/adr/`.

Общего handbook нет и не будет. Все решения проекта — здесь.

### Вложенные code blocks

LLM забывают про вложенность бэктиков, документы рвутся.

Правило обязательное:

- Внешний блок — N бэктиков, каждый следующий уровень — N-1.
- Стандартный code block — 3 бэктика.
- Если внутри него нужен ещё блок — внешний 4, внутренний 3.
- Если внутри того — ещё — внешний 5, средний 4, внутренний 3.
- И так далее.

### Форматирование Markdown

Правила для всех `.md` файлов в проекте (README, ADR, doc):

- **Длина строки — до 80 символов.** Исключения: блоки кода,
  таблицы, длинные URL, которые нельзя разорвать.
- **Таблицы — без выравнивания пробелами.** Разделитель
  `| --- | --- |`, содержимое ячеек — минимально. Пример:

  ```
  | Поле | Тип | Назначение |
  | --- | --- | --- |
  | `post_id` | BIGINT UNSIGNED | PK |
  ```

  Не так (выравнивание пробелами не используем):

  ```
  | Поле      | Тип              | Назначение |
  | --------- | ---------------- | ---------- |
  | `post_id` | BIGINT UNSIGNED  | PK         |
  ```

- **Заголовки — ATX** (`#`, `##`), один пробел после решётки.
- **Списки — дефис** (`-`), не звёздочка.
- **Блоки кода — тройные бэктики с языком**: `php`, `json`,
  `bash`, `markdown`, `yaml`, `neon`. Если язык не важен —
  `text`.
- **Курсив и жирный — `*` и `**`**, не подчёркивания.
- **Ссылки — inline** (`[текст](url)`), не reference-style.

**Инструмент форматирования в этом ADR не фиксируется.** Правила
соблюдаются вручную. Когда появится универсальное решение для
всех проектов — отдельный ADR-PROC-XXXX, где будет выбран
форматтер и настроен CI.

### Шаблон ADR

````markdown
# ADR-<ТИП>-<NNNN>: Краткое название
**Статус:** Proposed | Accepted | Deprecated | Superseded by ADR-XXX-XXXX
**Создано:** YYYY-MM-DD
**Обновлено:** YYYY-MM-DD

## Контекст

## Решение

**Пример:**

```php
public function example(): bool {
    return true;
}
```

## Последствия

## Альтернативы

## Ссылки

## Открытые вопросы (опционально)

````


**Правила заполнения:**

- **Контекст** — 2–5 строк. Без воды.
- **Решение** — список правил или описание. Одно правило — одна строка.
- **Последствия** — плюсы, минусы, риски. Без «только плюсов».
- **Альтернативы** — обязательны. Если альтернатив не было — это не решение,
  а констатация.
- **Ссылки** — три типа: «зависит от», «уточняется в», «связано с». Если
  пусто — так и пишем «нет».
- **Открытые вопросы** — опционально. Если есть — реальные вопросы.

### Ссылки между ADR

Три типа:

- **Зависит от** — без этого ADR правило не работает.
- **Уточняется в** — детали вынесены в другой ADR.
- **Связано с** — соседние решения, не обязательные, но полезные.

### Статусы

- **Proposed** — предложен, обсуждается, ещё не принят.
- **Accepted** — принят, действует.
- **Deprecated** — устарел, но ещё не заменён.
- **Superseded** — заменён другим ADR.

**Переход Proposed → Accepted:**

- Все открытые вопросы решены или явно отложены.
- Нет критических противоречий с другими ADR.
- Автор явно принимает решение.
- В `index.md` статус меняется на `Accepted`, обновляется дата `Updated`.

### Индекс ADR

Индекс — `doc/adr/index.md`.

Содержит:

- типы;
- статусы;
- таблицу: ID, название, статус, Created, Updated.

Ссылки на несуществующие ADR — без ссылки, только ID и `TBD` в статусе.

**TBD-записи** остаются в индексе до создания документа. Если TBD висит
дольше 6 месяцев — либо создаётся ADR, либо запись удаляется из индекса.

### Документация и ADR

- В документации — обзор и ссылки на ADR.
- В ADR — решения.
- Не пересказывать ADR в документации. Если нужно объяснить «почему» —
  ссылка на ADR, а не пересказ.

## Последствия

**Плюсы:**

- Единый формат решений.
- Документация для работы, не для вида.
- LLM и человек читают одно и то же.
- Один уровень ADR — не надо помнить, куда класть новый документ.
- Ссылки между ADR делают систему решений связной.

**Минусы:**

- Нужна дисциплина: ссылки, статусы, шаблон.
- Обновление `Updated` при содержательных правках — ручная работа.

**Риски:**

- ADR могут устаревать. Решение: пересмотр по событию (при появлении
  противоречий) и раз в квартал.
- Документация и ADR могут дублироваться. Решение: в документации — ссылки,
  не пересказ.

## Альтернативы

- **Один большой ADR вместо нескольких.** Отклонено: LLM путают правила из
  разных областей, файл жрёт контекст.
- **Документация на русском.** Отклонено: продукт класса А, README — для
  англоязычной аудитории WordPress.org.
- **Нет документации, только ADR.** Отклонено: новому участнику (или мне
  через год) нужен вход, а не решения.
- **Стандартные шаблоны ADR из интернета.** Отклонено: они для команд и
  отчётности, не для одиночки с LLM.
- **Два уровня ADR (handbook + продукт).** Отклонено: один проект — один
  уровень, проще.
