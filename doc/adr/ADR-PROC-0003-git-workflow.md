# ADR-PROC-0003: Git-workflow

**Статус:** Proposed
**Создано:** 2026-10-02
**Обновлено:** 2026-10-02

## Контекст

Проекту нужен предсказуемый git-workflow: как называть ветки, как писать
коммиты, как готовить релизы. Без этого LLM каждый раз будет предлагать свой
порядок, а история коммитов станет нечитаемой.

Отдельная задача — **релизы**. Плагин публикуется в WordPress.org, значит, в
дистрибутив не должны попадать файлы разработки: `.git`, `.github`, тесты,
конфиги линтеров, `node_modules`.

## Решение

### Формат коммитов

Conventional Commits. Язык сообщений — **английский**.

Типы:

| Тип | Когда |
| --- | --- |
| `feat` | Новая функциональность |
| `fix` | Исправление бага |
| `docs` | Документация (README, ADR, комментарии) |
| `test` | Тесты |
| `refactor` | Рефакторинг без изменения поведения |
| `chore` | Сборка, зависимости, конфиги |
| `ci` | CI/CD |

Формат: `<type>(<scope>): <subject>`. Scope — опционально, но полезен:
`feat(collector): add taxonomy sorting`, `fix(cache): invalidate on term change`.

Тело коммита — опционально. Если изменение неочевидно, тело объясняет
**почему**, а не **что** (что видно из diff).

### Ветвление

**Trunk-based.** Всё в `main`. Без долгоживущих веток, без PR-флоу для
одиночной разработки.

Для крупных фич, которые нельзя разбить на серию атомарных коммитов, допускается
короткая feature-ветка (`feat/collector-sorting`), которая вливается в `main`
через `--no-ff` merge. Ветка живёт не дольше одного цикла работы (день-два).

Теги — `vX.Y.Z` (semver). Аннотированные (`git tag -a`), не лёгкие.

### Атомарность

Один коммит — одно логическое изменение. Не смешивать:

- Рефакторинг и функциональность.
- Форматирование и логику.
- Правки в разных подсистемах (collector и renderer — два коммита).

Тест и код, который делает тест зелёным, — **в одном коммите**. Иначе коммит
не самодостаточен: после него тесты падают.

### Порядок первого коммита

1. Скелет репозитория: `.gitignore`, `.gitattributes`, `composer.json`,
   `news-feed-factory.php` (пустой bootstrap), `README.md`.
2. ADR-набор: `doc/adr/` целиком, включая `index.md`.
3. Код — по мере разработки, атомарными коммитами.

### `.gitignore`

Исключает из **git-истории**:

```
/vendor/
/node_modules/
/.phpunit.result.cache
/phpunit.xml
/wp-env/
*.mo
*.log
.DS_Store
```

`*.pot` — **не игнорируется**, коммитится: это исходный файл для переводчиков.

### `.gitattributes` — канонический механизм сборки дистрибутива

**Выбран один механизм — `git archive` + `.gitattributes` с атрибутом
`export-ignore`.**

Обоснование:

- Git-нативный, не требует внешних инструментов (WP-CLI, Composer, Node).
- Один файл для сопровождения.
- Работает в любой среде, где есть git.
- Не путается с другими инструментами: `.distignore` (формат WP-CLI) и
  `.gitattributes` — это **разные механизмы для разных инструментов**, а не
  «основной и подстраховка». `git archive` про `.distignore` не знает.

Базовый набор:

```
/.gitattributes     export-ignore
/.gitignore         export-ignore
/.github            export-ignore
/tests              export-ignore
/doc                export-ignore
/README.md          export-ignore
/composer.json      export-ignore
/composer.lock      export-ignore
/phpunit.xml.dist   export-ignore
/phpcs.xml.dist     export-ignore
/phpstan.neon.dist  export-ignore
/.editorconfig      export-ignore
/.phpunit.result.cache export-ignore
.DS_Store           export-ignore
```

**Важно:** `readme.txt` **не исключается** — это файл для WordPress.org.
`README.md` **исключается** — это для разработчиков.

`vendor/` — исключается, если зависимости ставятся через Composer на стороне
пользователя. Если плагин поставляется с vendor (bundled) — `vendor/` не
исключается, но об этом нужно отдельное решение. Пока считаем, что зависимостей
для рантайма нет (только dev).

### Сборка релиза

Локально:

```bash
git archive --format=zip --output=build/news-feed-factory.zip HEAD
```

Или через `git archive` с префиксом (чтобы внутри zip была папка плагина):

```bash
git archive --format=zip --prefix=news-feed-factory/ \
  --output=build/news-feed-factory.zip HEAD
```

**Не используется** `wp dist-archive` и `.distignore`. Если в будущем
понадобится WP-CLI-совместимая сборка (например, из-за конкретного CI), это
будет отдельным решением с явным указанием, почему появляется второй механизм
и как он синхронизируется с `.gitattributes`.

### Релизный цикл

1. Все тесты зелёные на `main`.
2. Обновлены версии: `Version:` в `news-feed-factory.php`, `Stable tag:` в
   `readme.txt`, `CHANGELOG.md` (если есть).
3. Коммит: `chore(release): bump version to X.Y.Z`.
4. Тег: `git tag -a vX.Y.Z -m "Release X.Y.Z"`.
5. Пуш тега: `git push origin main --tags`.
6. Сборка zip через `git archive`.
7. Ручная проверка артефакта: в zip нет `.git`, `tests`, `doc`, `README.md`
   и прочего мусора из `.gitattributes`.
8. Деплой в SVN WordPress.org (автоматически по тегу или вручную).

### Версионирование

Semver:

- **Major** — несовместимые изменения (схема таблицы, формат настроек).
- **Minor** — новая функциональность (новый рендерер, новое поле).
- **Patch** — багфиксы, совместимые улучшения.

До 1.0.0 — допускаются ломающие изменения в minor.

## Последствия

**Плюсы:**

- Предсказуемая история коммитов.
- LLM работают по одному шаблону, не изобретают.
- Релизы чистые: `.gitattributes` гарантирует, что в zip нет мусора.
- Один механизм сборки — не нужно синхронизировать `.distignore` и
  `.gitattributes`.
- Trunk-based — минимум церемоний для одиночной разработки.

**Минусы:**

- `.gitattributes` не поддерживается популярными WordPress-действиями
  (10up/action-wordpress-plugin-build-zip по умолчанию читает `.distignore`).
  Если будем использовать такие Actions — либо кастомный шаг сборки, либо
  отдельное решение по `.distignore`.
- Ручная сборка требует помнить про `--prefix`.

**Риски:**

- Забыть добавить запись в `.gitattributes` при создании новой dev-папки →
  мусор в релизе. Решение: добавлять запись в `.gitattributes` в том же
  коммите, что и новую папку.
- `vendor/` может понадобиться в рантайме, если появятся runtime-зависимости.
  Решение: при появлении — отдельное решение и правка `.gitattributes`.

## Альтернативы

- **`.distignore` + `wp dist-archive` как основной механизм.** Отклонено:
  требует WP-CLI, специфичен для WordPress-тулинга. Если понадобится — вернёмся
  отдельным решением.
- **Два механизма (`.gitattributes` + `.distignore`).** Отклонено: два файла
  нужно синхронизировать вручную, они расходятся при добавлении новых путей.
  Один канонический проще.
- **Git-flow (develop/release/hotfix).** Отклонено: избыточно для одиночной
  разработки.
- **PR-флоу для каждого изменения.** Отклонено: нет ревьюера, кроме меня
  самого.
- **Без `.gitattributes`, вручную собирать zip.** Отклонено: забывается, мусор
  попадает в релиз.
- **Русские сообщения коммитов.** Отклонено: код на английском, коммиты — часть
  кода.

## Открытые вопросы

- **`vendor/` в дистрибутиве:** исключаем сейчас, но если появятся runtime-
  зависимости — вернуться к этому решению.
- **Автоматизация деплоя:** CI для сборки и деплоя в SVN WordPress.org —
  отдельное решение, когда появится первый релиз. Если к тому моменту
  понадобится `.distignore` для 10up-действий — отдельный ADR с обоснованием.
